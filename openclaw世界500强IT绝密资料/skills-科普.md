# TLDR

- 设计技能时，过于详尽有时弊大于利，Agent 会难以提取相关信息。简洁、分步骤的指导并辅以可运行的示例，通常比详尽的文档更有效。如有很多特殊情况，也应优先考虑是否由 Agent 自身判断处理
- 以 "渐进式披露" 的方式设计技能
- 当多种工具或方法都可行时，选择一个默认方案并简要提及备选方案，而不是把它们并列为同等选择

# 什么是技能

技能是包含一个 `SKILL.md` 文件的文件夹。

SKILL.md 文件至少要包含元数据 `name` 和 `description` 。以及指示 Agent 如何执行特定任务的说明。

技能还可以包含脚本 scripts、模板 templates 和参考资料 reference。

示例结构如下

```
demo-skill/
├── SKILL.md          # 必需：说明 + 元数据
├── scripts/          # 可选：可执行代码/脚本
├── references/       # 可选：文档
└── assets/           # 可选：模板、资源
```

# 技能如何工作

技能使用渐进式披露（progressive disclosure）来高效管理上下文

- **发现**： 在启动时，Agent 只加载每个可用技能的名称（name）和描述（description），足以判断何时可能相关
- **激活**： 当某项任务与某个技能的描述匹配时，Agent 会将完整的 SKILL.md 说明读入上下文
- **执行**： 代理按照说明操作，必要时可**选择性加载引用的文件或执行捆绑的代码**

# SKILL.md 文件

格式： 以一个**包含 YAML 页眉**和 **Markdown** 正文格式

这里可以注意到，`name` 和 `description` 是必须的。正文包含实际说明，对结构或内容则没有特定限制。

```markdown
---
name: pdf-processing
description: 提取 PDF 文本、填写表单、合并文件。处理 PDF 时使用。
license: Apache-2.0
metadata:
  author: demo
  version: "1.0"
---

# PDF 处理

## 何时使用此技能
当用户需要处理 PDF 文件时使用此技能...

## 如何提取文本
1. 使用 pdfplumber 进行文本提取...

## 如何填写表单
...
```

## SKILL.md 内容规范

| 字段          | 必填 | 约束                                                                 |
| ------------- | ---- | -------------------------------------------------------------------- |
| name          | 是   | 最多 64 个字符。仅允许小写字母、数字和连字符。不得以连字符开始或结束 |
| description   | 是   | 最多 1024 个字符。不能为空。描述该技能的作用及何时使用               |
| license       | 否   | 许可证名称或对捆绑许可证文件的引用                                   |
| compatibility | 否   | 最多 500 个字符。指明环境要求（目标产品、系统软件包、网络访问等）    |
| metadata      | 否   | 额外元数据的任意键值映射                                             |
| allowed-tools | 否   | 以空格分隔的字符串，列出该技能可能使用的预先批准的工具。（实验性）   |

### name

- 不得超过 64 个字符
- 仅可包含 unicode 小写字母数字字符（ a-z ）和连字符（ - ）但不能以（ - ）开头或结尾，也不能包含连续的连字符（ -- ）
- **name 必须和父目录（skill 的目录名）名称保持一致**。假设 skill 目录叫做 demo-skill，则 name 也必须叫 demo-skill

### description

- 是否触发技能的全部责任落在描述上(description 不是简介，而是路由规则)。如果描述没有传达该技能何时有用，Agent 就不会知道要调用它。另外一个重要的细微之处是：Agent 通常只在任务需要超出其自身处理能力的知识或能力时才会查阅技能（除非用户手动指定调用该技能）。
- 不得超过 1024 个字符
- 应同时描述该技能的功能以及何时使用它。像“阅读这个 PDF”这样简单的一步请求，即便描述完全匹配，也可能不会触发 PDF 技能，因为 Agent 可以用基本工具处理它。
- 应包含有助于代理识别相关任务的特定关键词
- 好例子： "从 PDF 文件中提取文本和表格，填写 PDF 表单，并合并多个 PDF。适用于处理 PDF 文档或用户提到 PDF、表单或文档提取的情况。"
- 坏例子： "PDF 处理助手"
- 构建有效的描述
  - 使用祈使句：“在……情况下使用此技能”，而不是 “此技能会……”。因为 Agent 需要**决定是否调用，所以要告诉它何时调用**
  - 关注用户意图，而非实现细节。描述用户想要达成的目标，而不是技能的内部机制。
  - 倾向于积极明确。明确列出技能适用的场景，包括用户未直接指出领域的情况：“即使他们没有明确提到 'CSV' 或 '分析'”

### license

- 指定应用于该技能的许可证，建议保持简短（要么为许可证名称，要么为随附许可证文件的名称）
- 示例： Proprietary. LICENSE.txt has complete terms

### compatibility

- 不得超过 500 个字符
- 仅在你的技能有特定环境要求时才应包含。指明预期的产品、所需的系统包、网络访问需求等
- 示例：Requires Python 3.14+ and uv

### 正文内容

- 没有格式限制。撰写任何有助于代理有效完成任务的内容。但推荐包含以下章节
  - 逐步操作说明 Step-by-step instructions
  - 输入和输出示例 Examples of inputs and outputs
  - 特殊情况 Common edge cases
  - 注意事项 gotchas
- 为了上下文考虑，建议正文部分少于 5000 tokens
- 许多技能中价值最高的内容是一份 “注意事项” 清单，这些是违反合理假设的特定环境事实。它们不是一般性的建议（“适当处理错误”），而是对 Agent 在未被告知时会犯的错误的具体纠正。当 Agent 犯了你需要纠正的错误时，请将该纠正添加到 注意事项（gotchas） 部分。这是迭代改进技能的最直接方式之一

```markdown
## 注意事项

- 用户 ID 在数据库中为 `user_id`，在认证服务为 `uid`，在计费 API 中为 `accountId`。这三者指的都是同一个值。
- `/health` 端点只要 Web 服务器运行就会返回 200，即使数据库连接中断也会如此。使用 `/ready` 来检查完整的服务健康状况。
```

# 可选目录

> 在技能中引用其他文件时，请使用相对于技能根目录的相对路径。并且建议保持与 SKILL.md 文件的一层深度（避免深度嵌套的引用链）。例如

```markdown
有关详细信息，请参见[参考指南](references/REFERENCE.md)。

运行提取脚本：
scripts/extract.py
```

## scripts

- 包含可以运行的可执行代码。
- 记录清楚运行这些脚本的依赖关系。提供有用的错误信息并优雅的处理特殊情况。
- 支持的脚本类型取决与 Agent 运行在哪个平台以及环境是否依赖运行。例如 Linux 通常可运行 Python 脚本（提前安装 python 解释器）、Bash 脚本

## references

- 包含在需要时可阅读的附加文档
  - REFERENCE.md 详细技术参考
  - FORMS.md 表单模板或结构化数据格式
  - 其他特定领域/模块文件，finance.md, legal.md 等等...
- 保持每个参考文件的专注性。Agent 会按需加载这些文件，文件越小对上下文的占用就越少
- 当某个技能确实需要更多内容时，应将详细的参考资料移至 references 或类似目录中的单独文件。关键在于告诉代理何时加载每个文件。“如果 API 返回非 200 状态码，则读取 references/api-errors.md ” 比通用的 “参见 references/ 以获取详细信息” 更有用。这让 Agent 按需加载上下文，而不是一开始就全部加载，这正是渐进式披露的设计初衷。

## assets

- 包含静态资源，如图片、文档模板、配置模板、数据文件等等...
