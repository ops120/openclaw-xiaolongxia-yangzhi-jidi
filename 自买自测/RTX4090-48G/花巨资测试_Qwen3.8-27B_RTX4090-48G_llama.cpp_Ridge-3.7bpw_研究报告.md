## 0. 结论（基于 7 份日志实测）

### 0.1 一句话

> **Ridge-3.7bpw（11.72 GiB）+ llama.cpp 在 4090 48G 上把 192K 上下文跑成了"日常可用"**：79.5 分钟真实 Agent 流量、132 个任务、上下文最高 191,649 token，decode 中位 **41.5 tok/s**（短上下文 50–60，100K+ 上下文仍 42–44），prefill 中位 **1,458 tok/s**（峰值 2,383），全程显存恒定 **24,078 MiB（49%）**，**零崩溃、零内存错误**（仅 1 起客户端请求超 192,000 上限被拒）。
> **MTP2 单流短上下文冲到 98.4 tok/s**（基线同档 ~60，约 1.6×），接受率 47.7%（mean len 1.95）；但 **262144×4 slot 的 MTP 配置在并发下会撞 KV**：44 次 `failed to prepare attention ubatches` + 43 次 KV 满重试，单请求 tg_3s 最低掉到 0.78 tok/s。
> **256K 单 slot 可行**：138,107 token prompt（95.3 s，平均 1,449 tok/s）后在 ~140K 上下文上稳定 decode **42.3 tok/s**。
> **256K 无 MTP 档因参数语法错误未测**（`--override-kv qwen35.context_length=262144` 缺 `int:` 类型前缀）。

### 0.2 推荐配置（基于本批数据）

| 优先级 | 配置 | Decode | 说明 |
|---|---|---:|---|
| ⭐ **首选** | **192K + 无投机 + 4 slot（基线档）** | 中位 **41.5**（短 ctx 50–60 / 100K+ ctx 42–44）| 79.5 分钟零故障，本批证据最厚的档 |
| ⭐ 次选 | **256K + MTP2 + 1 slot** | **42.3** @ ~140K ctx（峰值 52.3）| 单流长上下文主力；256K 满载未测 |
| ⚠️ 有条件 | **MTP2 + 低并发 + 按需 ctx** | 短 ctx 单流 **86–98**（~1.6×）| 必须把 ctx 从 262144 降到实际需求、并发 ≤2，否则撞 KV（§5.2）|
| ❓ 未测 | MTP6 | — | 只启动无流量 |
| ❌ 失败 | 256K 无 MTP | — | `--override-kv` 语法错误，修复见 §3.4 |

## 3. 逐日志详解

### 3.1 192K 基线（主证据）

**运行画像**：79.5 分钟（日志相对时间 0.00 → 79.29），132 个任务，前缀缓存复用明显（大量 `f_sim_best ≥ 0.85` 的 slot 选择）。monitor 侧（17:44–18:28）观察到生成时段 GPU 利用率中位 **92%**、峰值 100%——**纯 GPU 带宽受限型 decode**。

**Decode 统计**（1,006 个 3 秒级 tg 采样窗口）：

| 口径 | min | q1 | **中位** | q3 | max |
|---|---:|---:|---:|---:|---:|
| tg 全窗口（n=1006）| 32.87 | 37.47 | **41.53** | 46.94 | **59.99** |
| 分桶 | 30–39: 465（46%）| 40–49: 388（39%）| 50–59: 153（15%）| | |
| 按任务 eval（生成≥100 tok，n=121）| 32.88 | 36.34 | **43.58** | 48.63 | 59.64 |
| monitor gen_tps（420 条）| — | p10 34.8 | **42.4** | p90 53.2 | 59.8 |

> 三路数据（日志 tg / 任务 eval / monitor）中位 41.5 / 43.6 / 42.4，**互差 <5%，交叉验证通过**。

**Decode 随上下文的变化**（本批最重要的曲线）：

| 上下文位置 | 证据 | tg |
|---|---|---:|
| ~13K（task 73，开局）| `2.21.957 n_gen=181, tg=59.99` | ~60 |
| ~30–46K（task 661/1163/2444）| tg 51–56 | ~51–56 |
| ~102K（task 137557，尾段）| `79.16–79.28 tg=43.64→42.32` | ~42–44 |
| 152K prompt 处理中（快照 18:28:30）| 快照 `gen.tg=43.54`，同时 `prompt.n_tokens=152764` | 43.5 |

> **从 13K 到 102K+ 上下文，decode 只从 ~60 掉到 ~42（约 -30%），没有塌方。** 这是混合注意力架构（大部分层是 GDN 线性注意力，decode 每步只读固定状态）+ 小量化体（11.72 GiB）共同作用的结果。对照同卡 vLLM 0.19.1 在同上下文区间 1.8–3.2 tok/s（框评 §3），差距是数量级的。

**Prefill**：≥1000 token 的请求（n=39）中位 **1,457.6 tok/s**，峰值 **2,383.5**（task 401，12,075 tok）；瞬时窗口最高 ~2,692（task 2 首窗口）。随上下文增长衰减：138K prompt 尾部降至 ~1,449–1,469（256k_mtp2 全程实测）。

**边界与错误**（全日志仅 2 起异常）：
1. `43.15.447 send_error: task 78661, request (192205 tokens) exceeds the available context size (192000)`——客户端请求超限 205 token，服务端正确拒绝；
2. `1.19.287 cancel task`——客户端主动取消 1 起。
**无崩溃、无 KV 错误、无 ubatch 错误。**

**显存**：24,078 MiB 恒定（KV unified 预分配）——上下文从 0 涨到 191,649 期间显存曲线是平的。剩 25,062 MiB 余量未用。

### 3.2 192k_mtp2（262144 / 4 slot / MTP2）

**配置差异**：相对基线把 ctx 提到 262,144 并开启内置 MTP 草稿（k=2）。**运行 7.5 分钟，16 个任务**，负载是"3 个大上下文请求 + 若干小请求"的并发混合。

**加速上限（单流短上下文）**：

| 时间 | 任务 | tg | 说明 |
|---|---|---:|---|
| 0.22.452 | task 9 | **98.39**（tg_3s 98.71）| 本批所有日志的最高 decode 值 |
| 0.25–0.28 | task 9 | 86.6–86.7 | 持续 ~11 s |

> task 9 上下文仅 3,786 token、单流。对照基线同档峰值 59.99：**MTP2 上限 ~1.6×**。

**接受率**（7 个有 draft 统计的任务，4 个生成≥50 token）：

| 指标 | 数值 |
|---|---|
| 加权接受率 | **47.7%**（全部 7 行收尾统计汇总：2,048 / 4,290；其中生成≥50 tok 的 4 个任务为 2,042 / 4,284，同为 47.7%）|
| mean len（任务级中位）| **1.95**（上限 = 1 + k = 3）|
| 参考：4090-24G llama MTP2（NVFP4 Q5_K GGUF，短样本）| 59.7%，mean len 2.19（引《Qwen3.8-27B-NVFP4-llama-server-MTP部署实测-4090.md》§5）|

> 接受率 47.7% 低于 24G 卡的 59.7%，口径差异（本批上下文更长、混合真实流量）如实保留；两者同为 k=2，方向一致：**MTP 在这台机器上有效但收益温和**。

**病理段（KV 争用）**：`5.40` 起，3 个大请求（task 431 → 132,250 tok、task 2115 → 65,921、task 2049 → 64,404）+ 小请求并发，出现：

- **44 次** `E init_batch: failed to prepare attention ubatches`
- **43 次** `failed to find free space in the KV cache, retrying with smaller batch size`（2048→1024→512→256→128 逐级降批）
- **6 次** `Context size has been exceeded`（task 2172 等）
- 单请求 tg_3s 最低 **0.78–0.93**（task 431/2659 被大 prefill 饿死）

> 结论：**262144 × 4 slot 的 KV 预留 + MTP 草稿额外占用在并发下超卖**。这不是崩溃（服务活着、错误可恢复），但吞吐体验崩坏。规避：ctx 按需设置、`-np` 降到 1–2（§8）。

### 3.3 192k_mtp6（未测）

启动成功（`creating MTP draft context`，n_ctx_slot=262144，4 slot，listening on :8000），日志 6.4 秒、零请求。**只能证明 MTP6 可启动**，无性能数据。

### 3.4 256k 基线（启动失败 + 修复方法）

```
E cmn string_parse: invalid type for KV override 'qwen35.context_length=262144'
error while handling argument "--override-kv"
```

**原因**：`--override-kv` 要求 `KEY=类型:值` 格式。**修复**：`--override-kv qwen35.context_length=int:262144`。
**影响**：256K 无 MTP 基线缺失——本报告无法给出 256K 无投机档的 decode 数（只有 256k_mtp2 单流数据）。

### 3.5 256k_mtp2（262144 / 1 slot / MTP2 / kv_unified=false）

**单请求全流程**（本批唯一的 256K 配置实测）：

| 阶段 | 数据 |
|---|---|
| 启动 → 就绪 | 6.4 s（加载）|
| Prompt | **138,107 token / 95.29 s = 平均 1,449.3 tok/s**（起始 2,492 → 尾部 1,449，随上下文单调衰减）|
| Decode | n_gen 145 起：47.6 → **峰值 52.26** → 稳定 **42.3**（n=31 窗口，41.94–52.26）；生成至 3,974 token（~140K 上下文）时日志被拉回截断 |
| 显存/配置 | 1 slot、262144 ctx、kv_unified=false、MTP2 已武装（任务未完成，无接受率行）|

> **140K 上下文上 42.3 tok/s 的持续 decode**——与 192K 基线在 102K 上的 42–44 完全一致，说明该卡该量化体下 **128K–192K 区间的 decode 瓶颈是权重带宽而非上下文长度**。

## 4. Ridge-3.7bpw 量化体评估

| 维度 | 数据 | 评注 |
|---|---|---|
| 体积 | 12,588,191,744 B = **11.72 GiB**（27.32B 参数 → **3.69 bpw**）| 约为官方 FP8（28.95 GiB，vLLM 实测口径）的 **40%** |
| ftype 标签 | 报 "IQ2_M - 2.7 bpw" | **枚举失配，不可信**；以体积为准 |
| 显存占用 | 模型 + 预分配 KV 共 **24,078 MiB（49%）** | 48G 卡留 25 GiB 余量 |
| Decode 带宽画像 | 41.5 tok/s × 11.72 GiB ≈ 486 GiB/s 有效读取 | 低于 4090 理论带宽，符合 KV/注意力开销预期 |
| 精度 | **本批未测**（只有速度数据）| 3.7 bpw 属激进低比特，上线前应跑质量评测 |
| MTP 头 | 内置（`blk.64.nextn.*`）| 单文件部署，无需单独草稿模型 |

## 5. MTP 投机解码在 llama.cpp 上的画像

### 5.1 收益

| 场景 | 无投机 | MTP2 | 倍数 |
|---|---:|---:|---:|
| 短上下文单流（~3.8K）| 基线同档峰值 ~60 | **86–98.4** | **~1.5–1.6×** |
| 140K 上下文单流 | 42.3（基线外推同档 ~42）| 42.3（256k_mtp2，接受率未知）| **≈1.0×（未见收益）** |

> 256k_mtp2 在长上下文上没有表现出加速——但它的任务没跑完，接受率未知，**不能断定 MTP2 在长上下文失效**（也可能接受率低到收益被草稿开销吃掉）。缺"256K/192K 无 MTP 单流 A/B"，见 §9。

### 5.2 代价与坑

1. **KV 超卖**：262144×4slot + 草稿上下文 → 44 次 ubatch 失败 + 43 次降批重试（§3.2）；
2. **上下文超限错误翻倍出现**（6 次，基线档只有 1 起请求超限）——大 ctx 配置诱导客户端投大请求；
3. k 值未扫描：MTP6 只证明能启动，k=2/3/4/6 的接受率-收益曲线缺失。

## 10. 结论

### 10.1 一句话总结

> - **192K 在 4090 48G + llama.cpp + Ridge-3.7bpw 上是日用的**：41.5 tok/s 中位、100K+ 上下文不塌方、79.5 min 零故障、显存只吃 49%
> - **长上下文 decode 是本组合的招牌**：140K 上下文 42.3 tok/s——同卡 vLLM 0.19.1 在同区间只有 1.8–3.2（框评核心议题）
> - **MTP2 是"短上下文加速器"**：单流上限 98.4（~1.6×），接受率 47.7%；长上下文未见收益；262144×4slot 高并发配置有 KV 超卖病理
> - **256K 单 slot 可行**（138K prompt 95 s + 42.3 decode）；256K 无 MTP 档欠一个 `int:` 前缀没跑成
> - **欠账**：精度评测、长跑、构建号记录、256K 基线补测

### 10.2 关键证据链

| 事实 | 证据 |
|---|---|
| 79.5 min / 132 任务 / 零崩溃 | 192k.log：132 launch/release 配对；唯一错误 = 192,205>192,000 请求拒绝 |
| decode 中位 41.5 | 日志 tg n=1006；任务 eval n=121 中位 43.6；monitor gen_tps n=420 中位 42.4 |
| 100K+ 上下文 42–44 | task 137557（ctx 102,386）tg 42.3–43.6；快照 18:28:30（152,764 prompt 并行）tg 43.54 |
| prefill 中位 1,458 / 峰值 2,384 | ≥1000 tok 请求 n=39 |
| MTP2 上限 98.39 | 192k_mtp2.log `0.22.452 task 9`（ctx 3,786）|
| MTP2 接受率 47.7% / mean len 1.95 | 7 行收尾统计汇总 2,048/4,290（生成≥50 tok 的 4 任务同率）|
| KV 争用病理 | 44× `failed to prepare attention ubatches` + 43× KV 降批重试 + 6× ctx exceeded |
| 138K prompt 95.29 s / 1,449 tok/s | 256k_mtp2.log progress 1.00 行（时间戳差与自报 t 互证：95.31 vs 95.29）|
| 140K ctx decode 42.3 | 256k_mtp2.log tg 序列（41.94–52.26，n=31）|
| 显存 24,078 MiB 恒定 | history 420 条全同值 + 快照 |
| 模型 11.72 GiB / 3.69 bpw | 快照 size/n_params |
| ftype 标签失配 | 快照 `IQ2_M - 2.7 bpw` vs 实测 3.69 |

### 10.3 报告局限

> 本报告不预测未实测的组合——不知道 256K 无 MTP 的 decode（欠一个 `int:` 前缀），不知道 MTP2 在 192K 干净单流下的精确加速比（mtp2 跑成了混合并发），不知道 Ridge-3.7bpw 的输出质量（只测了速度），也不知道这个 llama.cpp 构建的确切版本号。79.5 分钟是"观察窗口内零故障"，不是"长期稳定性证明"。跨参照（§7）全部来自不同批次/卡/版本，只做量级参考。
