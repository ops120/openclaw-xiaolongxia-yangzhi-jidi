## 0. 结论（基于 3 份数据实测）

### 0.1 一句话

> **4090 48G + FP8 + MTP3 能完整跑起 192K 配置**（这是 5090 32G 上装不下 MTP 的 192K）：短上下文（每请求 ≤~35K）单并发稳定 **~33 tok/s**、双并发 **~51 tok/s（峰值 80.8）**；中上下文（每请求 ~35–70K）双并发 **44–55 tok/s**；
> 但 **100K+ 长上下文 Decode 只有 1.8–3.2 tok/s**（每请求），prefill 可达 **15.6K tok/s**。
> MTP3 整体接受率 **61.1%**（mean acceptance length 2.9/4，第 3 位只有 0.51）——**k=3 的惩罚明确可见**。
> 实例在 **142.8K token 请求的 chunked prefill 期间**（与一个 2.6K decode 请求同批）触发 vLLM 0.19.1 GDN 线性注意力 **CUDA device-side assert 崩溃**（00:05:14），运行 3h21m。

### 0.2 推荐配置（基于本批数据）

| 优先级 | 配置 | Decode | 加速/说明 | 备注 |
|---|---:|---:|---|---|
| ⭐ **首选** | **192K + FP8 + MTP3**（本批唯一实测档）| 短上下文 ~33 单 / ~51 双并发；100K+ 上下文 1.8–3.2 | MTP 相对无加速收益见 §5.3（本批无 baseline，仅能对照手册预估）| 短上下文主力档 |
| ⭐ 次选 | 短上下文（每请求 ≤~35K）+ MTP3 | 双并发 51–66（峰值 80.8）| 23:04:43 峰值 80.8 tok/s | 双并发是甜点 |
| ⚠️ 注意 | 100K+ 单请求长上下文 | 1.8–3.2 tok/s | prefill ~10s/100K 可接受；decode 是瓶颈 | 客户端 timeout 要 >2min |
| ❌ 不稳 | vLLM 0.19.1 + 混合批大上下文 | — | 00:05:14 GDN CUDA assert 崩溃 | 换 vLLM 版本/降 max_num_seqs 规避 |
| ❓ 未测 | 无 MTP baseline / MTP2 / DFlash | — | 本批日志只有 MTP3 实例 | 见 §9 |

### 0.4 启动配置（本批 MTP3 实例，`non-default args` line 62）

```bash
vllm serve /hy-tmp/models/Qwen3.8-27B-FP8 \
  --max-model-len 192000 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.95 \
  --max-num-seqs 2 \
  --reasoning-parser qwen3 \
  --enable-prefix-caching \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}' \
  --served-model-name qwen3.8-27b-fp8 \
  --host 0.0.0.0 --port 8000
```

> 注意：`num_speculative_tokens=3` 与《Qwen3.8-27B-vLLM-MTP部署手册-单卡48G.md》推荐的 **k=2 @192K** 不同（手册依据：128K–192K 时 k=3 接受率降至 ~52%）。本批实测 k=3 整体接受率 61.1%、第 3 位 0.51——**与手册判断方向一致，k=2 值得补测**。

## TL;DR

| 维度 | 结论 |
|---|---|
| **192K 配置能不能跑** | ✅ 能——KV pool 14.04 GiB / 107,200 token，2.00x 并发上限；5090 32G 上 MTP 192K 装不下，4090 48G 装得下 |
| **短上下文（每请求 ≤~35K）** | MTP3 单并发 ~33 tok/s，双并发 ~51 tok/s（峰值 80.8）；中上下文（~35–70K）双并发 44–55 tok/s——**双并发是甜点** |
| **100K+ 长上下文 Decode** | **只有 1.8–3.2 tok/s（每请求）**——长上下文是 Ada 混合注意力模型的真瓶颈 |
| **Prefill** | 10.2K–15.6K tok/s（~102K token 首请求 TTFT ≈ 8–10 s）|
| **MTP3 接受率** | 整体 61.1%（199,376/326,292），mean len 2.9/4，pos1/2/3 = 0.78/0.63/0.51 |
| **稳定性** | 3h21m 后 GDN 线性注意力 CUDA device-side assert（142.8K 混合批），vLLM 0.19.1 已知路径 |
| **显存** | 峰值 46,286 MiB / 49,140 MiB（94.2%），KV 峰值 75.8% |
| **跨卡** | 5090 32G 长上下文 ~70 tok/s vs 本卡 1.8–3.2——**量级差距**（横评 §7）|

## 3. 资源分布（vLLM 启动期数据）

### 3.1 显存分配

| 资源 | 占用 | 来源 |
|---|---:|---|
| Model weights（含 MTP drafter，bf16 激活口径）| **28.95 GiB** | line 140 `Model loading took 28.95 GiB memory and 15.390559 seconds` |
| KV cache（实际可用池）| **14.04 GiB** | line 169 `Available KV cache memory: 14.04 GiB` |
| **运行峰值**（monitor 采样）| **46,286 MiB / 49,140 MiB = 94.2%** | `history.jsonl` `mem_used` 最大值（20:05–00:17 全段）|

> 48G 卡上 FP8 权重 28.95 GiB + KV 14.04 GiB ≈ 43 GiB，留 ~6 GiB 给激活/CUDA graph——`gpu_memory_utilization 0.95` 吃满。对比 5090 32G 参考报告（NVFP4 权重 19.78 + KV 7.33 = 27.11/31.36 GiB）：**48G 的 KV 余量是 32G 的 ~2 倍**，这是 192K+MTP 在 4090 上装得下的根本原因。

### 3.2 KV 缓存分配

```
Available KV cache memory: 14.04 GiB          (line 169)
GPU KV cache size: 107,200 tokens             (line 172)
Maximum concurrency for 192,000 tokens per request: 2.00x   (line 173)
```

> 该模型是**混合注意力**（GDN 线性注意力 + full attention），107,200 token 是 full-attention 层 KV 池；Mamba/GDN 状态另计。实测两个 ~100K+ 上下文请求同时在跑时 KV% 也只到 65–75%（§4.1），**池子对 192K×2 是够用的**（2.00x 上限实际被 `max_num_seqs=2` 封顶）。
> 运行期 KV 使用率：峰值 **75.8% @21:55:45**（21:52–21:59 大 prefill 簇期间），中位 30.5%。
>
> **KV% ↔ 上下文大小的换算**（混合模型，只能给估计）：崩溃 dump 显示 145,448 token 上下文（142,848+2,600）对应 KV 43.1%（≈46,200 池 token），映射系数 ≈ **3.1×**（约 1/3 层为 full attention；prefix cache 保留的块也计入使用率）。据此：KV 5–11% 池 ≈ 每请求 15K–35K 上下文；KV 32–43% ≈ 每请求 35K–70K（2 请求）。**下文各档"上下文"数值均为该换算的估计值，KV% 才是直接测量值。**

## 8. 推荐配置（基于本批数据）

### 8.1 三档适用性

| 档位 | 推荐方案 | 依据 |
|---|---|---|
| **短/中上下文（每请求 ≤~35K，Agent/Tool Calling 主力）** | **vLLM 0.19.1 + FP8 + MTP3（或降 k=2）+ max_num_seqs 2** | 双并发 51–66 tok/s（峰值 80.8），30 分钟无衰减（§4.2）|
| **长上下文（100K–156K）** | 同上，但**客户端 timeout ≥ 5 min、max_tokens 留足 thinking 额度** | prefill 10 s 级可接受；decode 1.8–3.2 tok/s，1K token 输出要 5–9 min（§4.1）|
| **192K 满载（2×192K）** | 理论可行（2.00x 并发上限）但**未实测**；且 0.19.1 GDN 崩溃风险 | 本批最大单请求 142.8K 即崩溃（§2）|
| **换版本/换卡** | 长上下文主力 → 5090 NVFP4（参考 §7）；Ada 预算 → 4090 48G 本配置 | 横评 §7 |

### 8.2 规避 GDN 崩溃（0.19.1 已知路径）

按风险收益排序：
1. **`--max-num-seqs 1`**：崩溃发生在 2 请求混合批（142.8K + 2.6K）。单并发牺牲 §4.2 的双并发甜点（~51→~33 tok/s），但长上下文稳。
2. **升级 vLLM**：0.20+ 修复线（手册 §方案选型 记载 0.20+ 默认 CUDA 13.0 构建，与驱动 570.211.01 冲突需 CUDA 12.8 构建/源编译——**升级前先在容器内验证驱动兼容性**）。
3. **避免"巨型请求 + 小请求"同批**：客户端侧错开 100K+ 请求与小请求的并发窗口。

### 8.3 MTP k 值

| k | 本批实测 | 5090 参考 | 结论 |
|:---:|---|---|---|
| 2 | 未测（前实例日志丢失）| 0.77–0.89，128K ~120 tok/s（1.76×）| **192K 配置首选**（手册同判）|
| 3 | **61.1%，mean len 2.9，pos3 0.51** | — | 短上下文可接受；长上下文建议降 k=2 |

## 10. 结论

> **本批数据下，Qwen3.8-27B 在 4090 48G + FP8 + MTP3（vLLM 0.19.1，192K 配置）上的画像：**

### 10.1 一句话总结

> - **4090 48G 跑 192K+MTP 是通的**——32G 卡（5090）装不下的配置（KV 缺 580 MiB），48G 卡完整启动并跑到 142.8K 上下文（KV 峰值 75.8%）
> - **短/中上下文是日用甜点**：双并发中位 51.2 tok/s（峰值 80.8），单并发 32.6
> - **100K+ 长上下文是 Ada 混合注意力的真瓶颈**：每请求 1.8–3.2 tok/s（prefill 却只要 ~10 s/100K）
> - **MTP3 接受率 61.1%（mean len 2.9/4）**——k=3 惩罚明确，192K 配置建议 k=2（待补测）
> - **稳定性**：3h21m 后 GDN fla kernel CUDA assert（大上下文混合批），0.19.1 + max_num_seqs=2 是风险组合，单并发或升版本可规避
> - **横评**：长上下文速度 5090 NVFP4（~70 tok/s）领先 ~25–40×；48G 的价值 = 容量 + 192K 可跑性，不是速度

### 10.2 关键证据链

| 事实 | 证据 |
|---|---|
| 192K + FP8 + MTP3 完整启动 | 主日志 line 169-173（KV 14.04 GiB / 107,200 token / 2.00x）+ line 185 就绪 |
| 短/中上下文双并发 ~51 tok/s | §4.2：23:51:58–00:02:29 连续 30 分钟 44–55 tok/s 窗口；峰值 80.8 @23:04:43 |
| 100K+ 长上下文 1.8–3.2 tok/s | §4.1：20:47:38–20:48:48（2.3–3.2，KV 40→66%）；00:04:19–00:05:10（0.8–2.5，142.8K 请求）|
| Prefill 10.2K–15.6K tok/s | 20:47:28（10,182，~102K token 首请求）；22:18:28（15,634.8 峰值）|
| MTP3 整体接受率 61.1% | 993 个 spec 窗口求和 199,376/326,292；pos1/2/3 = 0.78/0.63/0.51 |
| 显存峰值 46,286/49,140 MiB（94.2%）| `history.jsonl` mem_used 最大值 |

### 10.3 报告局限

> **本报告不预测未实测的组合**——
> 不知道 k=2 在本卡的确切接受率与 tok/s（前实例日志丢失），
> 不知道 2×192K 真满载会不会比 142.8K 混合批更早触发 GDN 崩溃，
> 不知道 DFlash2 在 4090 FP8 上能不能跑（草稿模型未部署），
